Why Orchestrata solves schedules without LLM tokens

At 7:30 a.m., a maintenance technician calls out. One urgent electrical job still has to be done by noon. Two routine jobs are already on the board. The dispatcher needs a revised plan: who moves, what stays, and which job has to wait.

Orchestrata uses mathematical optimization to make that decision. Give it the jobs, the people, the rules, and the trade-offs. The solve itself uses zero LLM tokens. It still uses compute; it just doesn’t require a model to read and rewrite the schedule.

How one decision becomes N+1 model calls

A common way to build an LLM planner is to ask the model to assign each job in turn, then ask it to assemble the final schedule. With N jobs, that’s N assignment calls plus one assembly call. If each call needs the same roster and rules, the workflow may send that context repeatedly. If each choice depends on the last, batching requests doesn’t remove that dependency.

N+1 is a workflow pattern, not a property of LLMs. You can batch jobs into one prompt, cache context, or have the model call a solver. But batching alone doesn’t ensure the plan meets the rules. The efficiency gain here comes from removing per-job model calls and repeated prompt context from the planning path. The solver still has a search problem to do, and runtime depends on the workload, rules, and time budget.

A valid assignment can still make for a bad plan

Take one available 9 a.m. slot per crew. Crew A is the only crew certified for electrical work. Crew B can handle either routine job. The electrical repair and the inspection are due by noon; a lower-priority filter change can wait. Travel and task durations are assumed to fit the stated slots.

If job-by-job assignment gives Crew A the inspection first, that choice is allowed on its own but leaves no qualified crew for the electrical repair. Looking at the jobs together preserves the scarce skill, meets both deadlines, and makes the deferral visible. This is a small worked example, not a timing benchmark.

Reliability means knowing what the plan satisfies

Required qualifications, availability, and no double-booking are rules a solver can check. Keeping existing assignments stable, reducing travel, or spreading work more fairly are preferences it can score. The reviewer can ask what changed and see which rule or trade-off drove the change. An explanation can also be checked against that evidence.

A feasible plan satisfies the rules included in the model. It isn’t necessarily the best possible plan. If the search stops without finding a valid plan, that doesn’t prove none exists. And no solver can compensate for an expired certification the source system never recorded. Solver status definitions illustrate these distinctions; PlanBench is a separate study of language-model planning, not an Orchestrata performance comparison.

Use language for the conversation and math for the plan

An LLM can turn “keep the morning jobs stable if you can” into a preference for the planner to review, or explain a change in plain language. The solve can run without it. That separation lets you measure what matters: hard-rule violations, jobs kept on time, overtime, schedule changes, end-to-end latency, and total compute cost. Any optional language-model calls can be measured separately.

Start with one disrupted shift. Compare the original and revised plans, check every required rule, and ask the dispatcher whether they’d act on the result. That’s a better test of a planning system than whether it can write a convincing schedule.
