# DNS steering and load-balancer integration guide

Use these references to map a traffic proposal to the provider you already run. The worked example reads a local snapshot and returns an advisory plan. It does not connect to a provider, reconcile configuration, run probes, or change live traffic.

DNS gives a resolver a destination. It does not choose a backend for each request. Cached answers and long-lived connections can continue using the old destination after a change. A load balancer makes a separate choice for new requests or new connections, depending on its protocol; session affinity and draining can keep earlier assignments in place. Treat a DNS weight as a share of eligible answers, not a promise about request volumes or a hard capacity limit. Resolver location is not always client location; do not use a DNS geolocation answer as proof of data residency. Some resolvers may serve expired records when refresh fails. [RFC 8767: DNS Serve-Stale](https://www.rfc-editor.org/rfc/rfc8767.html).

## Dry-run checklist

1. Read a permission-scoped inventory, the last approved policy version, effective DNS TTLs, enabled zones and origins, observed demand, and time-stamped health. Exclude credentials and request payloads from the snapshot.
2. Keep units separate: DNS answers and percentages, HTTP requests per second, concurrent requests, and network connections. Subtract reserve from measured service capacity and place no new load on an endpoint with unknown or stale health in the advisory model. Report demand with no eligible placement instead of silently violating a capacity or locality constraint.
3. Test the provider's actual behavior for all-unhealthy pools, zero weights, sticky sessions, drain, and loss of a full failure domain. Observe endpoint, request, and DNS signals separately. Mark any capability mismatch as requiring review, not as a deployable policy.
4. Review a scoped diff with the traffic owner. Any future rollout should use a bounded canary, stability windows before failback, and a rollback version. Compare error rate, tail latency, saturation, and unserved demand. This replay does not provide a deployment or a rollback guarantee.

## Preview two mappings offline

Put `provider-preview.mjs` next to the published `visual.json` and run with Node.js:

```sh
node provider-preview.mjs route53 normal global
node provider-preview.mjs gateway-api normal us-east
node provider-preview.mjs route53 region-unavailable eu-resident
node provider-preview.mjs gateway-api peak us-east
```

The first command previews relative DNS weights of 50, 35, and 15 for one sample market. The second previews the exact ratio 32:30:13 for one region's backend allocations. The last two return review reasons and no weights, rather than silently dropping unassigned lookup weight or assuming unserved requests could be distributed. Exit codes: 0 for an advisory result, 2 for a valid result requiring review, and 1 when input cannot be validated. These outputs contain example labels only, not records to apply, a Gateway manifest, or provider credentials. DNS and backend weights are ratios, not throughput or admission guarantees. [Route 53 weighted-record limits](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resource-record-sets-values-weighted.html) and [Gateway API HTTP traffic splitting](https://gateway-api.sigs.k8s.io/guides/user-guides/traffic-splitting/).
