Cover five branches with 500 operators

Each sample branch has 100 operators in four departments. The planner checks skills, proficiency, languages, experience, shifts, breaks, and voice or chat capacity. An operator can help another department only when the scenario allows it and their qualifications match.

In 60 independent staffing examples, the plans covered 480 positions. Orchestrata checked 94,990 possible assignments across those examples. A separate enumeration verified every result, including 23 assignments outside the operator’s home department.

Walk through the choices in one 30-minute window

For a 30-minute window in New York, the example checks every operator against each queue’s skills, language, experience, availability, breaks, and voice capacity. Those checks determine the eligible operators in the normalized solver input. No operator can cover two queues at once.

6 of 6 queues covered. The native solver checked 486 assignments; 324 met the hard rules. Hard score: 0. Soft score: -7.

Two billing queues prefer OP-001. The solver gives that operator the 9-point escalations preference and assigns eligible OP-002 to Spanish-language billing, incurring a 7-point penalty rather than 9.

The raw input also models typical and surge demand at 70% and 30% under sample assumptions. The audit calculates expected handling time and occupancy risk. Those values are context for a manager, not constraints the solver used.

Batch result: 1,440 checked assignments

Run the same checks on 240 independent coverage scenarios. Each has 60 operator profiles and six queues. Breaks, voice capacity, demand assumptions, and preference weights vary from one scenario to another. These are separate solves, not one company-wide roster or a speed benchmark.

The engine checked 13,598 combinations in total. Independent enumeration confirmed every result. 1,260 preferences were met and 180 were missed. The output preserves the assigned operators, the exclusions and reasons, the tradeoffs, and the verification for each scenario.

Cover three support queues at the same time

A support manager needs one agent per queue for a single coverage window. The IDs below identify eligible agents, not named people.

QueueEligible agent IDsAssigned agent ID
Billing escalations0, 22
Spanish-language support0, 10
Account recovery1, 21

The input puts each queue in variables[].name and its eligible agent IDs in variables[].domain. One all_different rule prevents double-booking. A prefer_value preference with soft weight 5 favors agent 2 for billing escalations. The exact result is [2, 0, 1] in queue order, with hard and soft scores of 0 and 8 combinations evaluated.

The fixture does not forecast arrivals, size staffing from service-level targets, schedule breaks, or send calls to agents.
