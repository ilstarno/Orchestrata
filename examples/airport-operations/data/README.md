# Airport stands and ground-crew planning

The data has two separate parts. `traffic.json` contains published 2025 passenger totals for the seven selected airports. Each entry identifies its publisher, coverage and rounding. Airports use different definitions for commercial, non-commercial and transit traffic, so the values are context, not like-for-like performance scores. No traffic total is used as an input to the worked schedule.

The two-hour example uses a generic facility, four modeled stands, nine sample flights and six ground teams. It is not an airport map, a live flight feed, an aircraft operating procedure, proof of approval, or an integration with an airport system. Flight IDs, stands, reserve capacities, staffing and times are example inputs; the windows and separation rules are not real operating limits.

- **Gate and apron.** The baseline assigns the first compatible stand in arrival order. The proposed pass enumerates eligible combinations and first minimizes held flights, then minimizes the number of passengers assigned to a remote stand. Stand capacity, border-handling compatibility, a step-free contact requirement, and the modeled five-minute occupancy buffer are hard rules. The baseline fits six flights; the recommended plan fits eight and holds one. That comes with a trade-off: 315 modeled passengers are routed via remote stands, compared with none in the baseline.
- **Aircraft turnaround.** Unload, cabin work, service and load need qualified teams, suitable shift windows and breaks, and sufficient time before departure. Dependent work cannot start before its preceding work is complete. A team needs four sample minutes to move to the other zone and cannot overlap its own work. The baseline uses teams only within their assigned zones; the comparison allows qualified cross-zone work and checks transfer time. The suggested schedule covers 30 of 36 tasks rather than 22, with six complete turns versus five. Crew placement is a deterministic earliest-eligible heuristic, not proof of an optimum. The comparison combines the change in gate placement and in team policy. It does not isolate either change.

Run `python3 replay.py` beside the JSON files to verify gate/crew checks and reproduce the published values, or `python3 replay.py --write` to regenerate the two outputs. The replay makes no network calls.
